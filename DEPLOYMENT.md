# Zahiri — deployment checklist

Work through this in order. Steps 1–4 get the app working end to end; step 5
(WhatsApp) is optional and can be done later without touching anything else.

---

## 1. MongoDB Atlas — allow Render to connect

Atlas blocks every IP by default, so the API will hang on startup until this is done.

- Atlas → your cluster → **Network Access** → **Add IP Address**
- Add `0.0.0.0/0` (allow from anywhere)

> `0.0.0.0/0` is broad. It is acceptable here because the database still requires
> the username and password in `MONGODB_URI`, but if you move to a paid Render
> plan you get static outbound IPs and should pin those instead.

Confirm the database user exists under **Database Access** with **Read and write
to any database**.

---

## 2. Push to GitHub

```bash
cd C:\Users\USER\zahiri
git add .
git commit -m "Zahiri: verification API + mobile app"
git branch -M main
git remote add origin https://github.com/<you>/zahiri.git
git push -u origin main
```

`.gitignore` already excludes `.env`, `credentials/`, `node_modules/`,
`mobile/android/`, and every `*.apk` and `*.keystore`. **Confirm before pushing:**

```bash
git status --porcelain | grep -iE "\.env$|keystore|credentials"   # must print nothing
```

---

## 3. Deploy the API to Render

- Render → **New → Blueprint** → pick the repo. `render.yaml` is detected.
- Render prompts for the secrets it will not store in git:

| Secret | Value |
|---|---|
| `MONGODB_URI` | your Atlas connection string, **with `/zahiri` before the `?`** |
| `NVIDIA_API_KEY` | `nvapi-…` from build.nvidia.com |
| `OPENROUTER_API_KEY` | `sk-or-v1-…` from openrouter.ai/keys |
| `WHATSAPP_APP_SECRET` | leave blank for now |
| `WHATSAPP_ACCESS_TOKEN` | leave blank for now |
| `WHATSAPP_PHONE_NUMBER_ID` | leave blank for now |

`JWT_SECRET` and `WHATSAPP_VERIFY_TOKEN` are generated by Render — you do not
supply them.

**Verify the deploy:**

```bash
curl https://<your-service>.onrender.com/health
# {"status":"ok","database":"connected","aiProviders":["nvidia","openrouter"],...}
```

If `database` is not `connected`, step 1 was missed.

**Seed the database** (once): Render → your service → **Shell**

```bash
npm run seed
```

**Create your admin account:** register in the app, then in the Render shell:

```bash
npm run grant -- admin you@example.com
```

`factchecker` and `admin` cannot be self-assigned at sign-up, so this is the only
way to create the first one.

---

## 4. Point the app at Render and rebuild the APK

```bash
cd mobile
# .env
EXPO_PUBLIC_API_URL=https://<your-service>.onrender.com
```

```bash
npx expo prebuild --platform android --clean
cd android && ./gradlew assembleRelease
# → android/app/build/outputs/apk/release/app-release.apk
```

Transfer the APK to the phone and install (Android will warn about an unknown
source — expected for a directly-installed APK).

> The URL is baked in at build time. Changing `EXPO_PUBLIC_API_URL` means
> rebuilding the APK.

### Expect a slow first launch

Render's free plan stops an idle instance. The first request after that waits
30–60s for a cold start. The app pings `/health` on launch, retries 502/503/504
with backoff, and shows a "Waking Zahiri up" banner instead of an error. Upgrade
to Starter ($7/mo) to remove the delay.

## 5. WhatsApp (optional)

Everything is already written; this only supplies credentials.

1. Register as a Meta developer at **developers.facebook.com** → *Get Started*.
2. **developers.facebook.com/apps/** → **Create app**.
3. Add WhatsApp to the app. **Which screen depends on how the app was created:**
   - Newer apps use the *use case* flow. Their **Add Product** page shows an
     empty "Available products" list, and WhatsApp is added at
     **Use cases → Add use cases → "Connect with customers through WhatsApp"**
     → *Save*. A "Connect on WhatsApp" entry then appears with its own
     Permissions, Quickstart, **API Setup**, and **Configuration** sections.
   - Older Business-type apps show it under **Add product → WhatsApp → Set up**.

   If WhatsApp appears in neither place, the app was created with a use case
   that excludes it — create a new app rather than fighting it.
4. **Create a business portfolio** when prompted. WhatsApp onboarding is blocked
   until one exists: business.facebook.com → create a portfolio with your real
   business name and contact details. Then return to the WhatsApp page.
5. You get a free test number that can message up to 5 numbers you nominate,
   which is enough to demo the whole flow without business verification.
6. Collect:
   - **WhatsApp → API Setup** → temporary access token and **Phone number ID**
   - **Settings → Basic** → **App Secret** (click *Show*)
7. Put those into Render → *Environment* as `WHATSAPP_ACCESS_TOKEN`,
   `WHATSAPP_PHONE_NUMBER_ID`, `WHATSAPP_APP_SECRET`. Copy the generated
   `WHATSAPP_VERIFY_TOKEN` out of Render.
8. **WhatsApp → Configuration → Webhook → Edit**:
   - Callback URL: `https://<your-service>.onrender.com/api/plugins/whatsapp/webhook`
   - Verify token: the value from Render
   - **Verify and save**
9. Still on that screen: **Manage** → subscribe to the **`messages`** field.
   Nothing arrives without this, and it is the step most often missed.

**Test:** send a message to the test number. You should get a verdict back in the
same thread.

> The temporary token expires in 24 hours. For anything lasting, create a
> **System User** under *Business Settings → Users → System Users*, assign the
> app, and generate a permanent token with `whatsapp_business_messaging` and
> `whatsapp_business_management`.

---

## After deploying

- **Rotate the credentials that were shared during development.** The Atlas
  password, NVIDIA key, and OpenRouter key were pasted into a chat transcript.
  Rotate all three and update Render:
  - Atlas → *Database Access* → edit user → **Edit Password**
  - build.nvidia.com → revoke and reissue the key
  - openrouter.ai/keys → revoke and reissue
- **Back up `mobile/credentials/`.** Losing the keystore means installed copies
  of the app can never be upgraded, only uninstalled and replaced.
- Watch the Render logs for `{"type":"security",...}` lines — those are the
  audit events (failed logins, lockouts, rejected uploads, blocked SSRF,
  injection attempts) and are worth alerting on.
